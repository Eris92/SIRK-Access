# Security model and limitations

- Public endpoints: receive page, OTP and read endpoints, OIDC and click telemetry. All state-changing application forms use antiforgery; OIDC callback handled by OIDC middleware with state/nonce/correlation. Rate limit by observed IP and OTP cooldown/attempts. Use upstream WAF and quotas before public exposure. Email OTP proves mailbox access, not identity or independent MFA if the link travels to the same mailbox; use separate trusted channels for bootstrap passwords. Prefer TAP where applicable. Force password reset/expiry through identity platform, not this portal.
- Internal notes bind to tenant-local object ID. Link is 256-bit random, stored as hash, passed in URL fragment and POST, not request URL. Browser temporarily keeps access code in sessionStorage for OIDC redirect. Treat endpoint compromise as secret compromise. No client-side E2E encryption; application must decrypt for delivery. AES-GCM per-note keys wrapped by DPAPI-protected ASP.NET key ring. Database expiry/revocation nulls ciphertext/key references, but SQLite WAL, free pages and backups can retain records. **Not guaranteed crypto-shredding**. Use short retention, encrypted disks/backups and implement independent destroyable key lifecycle before claiming irrecoverable deletion. Recipients can copy/screenshot plaintext. Do not restore notes from backup as live without reconciliation.
- Single IIS worker and local SQLite. Atomic consumption via immediate transaction. One-time code consumed on successful read; new OTP required for another read. Expired note denied even if cleanup service has not run. Audit event inserted within transaction for successful reads. Other administrative mutations and audit writes are not transactionally coupled yet. Audit database is writable by app identity; not immutable. Forward to independent SIEM with access controls, integrity and retention before production. UI click capture is best effort (disabled JS, network errors, rate limits); HTTP/resource authorization events are server-side. Raw keystrokes, input values, clipboard contents and coordinates deliberately not collected. IP/actor logs are personal data and require policy/retention. Audit viewer shows last 500 records. No CSV/syslog exporter yet.
- App roles and membership configured in Entra; claims remain valid until session expires (30 min). Admin GUI configures content, policy and access assignments; bootstrap identity and secrets stay outside GUI. No local password auth. MFA is an Entra CA prerequisite, not portal-enforced step-up. For higher sensitivity deploy separate enterprise app or authentication context with tested claims challenge.
- Resource links are HTTPS redirects, not reverse proxy. The target must enforce its own auth/MFA; use Entra App Proxy/KCD for legacy apps. File access is gated server-side, filenames are never used as filesystem paths; files served as attachment with SHA-256 stored. Manual approval is not malware scanning; deploy AV and package integrity checking. Restrict public URL destinations by allowlist and implement approval workflow if needed. No arbitrary network fetch/SSRF surface in launcher.
- Onboarding MVP: group resources by category and individually assign by object ID or role; dedicated package workflow, invitations, Graph/TAP automation, multiple grants per resource and group lookup are backlog. No VPN replacement for network-level access; HTTPS portal still exposed on TCP 443. No AD FS, no custom KCD in public app.
